# Decisions

Each decision is dated, with its reason.

- **D-P0-1 (2026-11-07) Toolchain.** Rust 1.98.1 with near-sdk 5.30 and cargo-near 0.22.0, the same pin as ~/scope. That keeps the reproducible-build image identical.
- **D-P0-2 (2026-11-07) Carry-over.** Files are copied into `operator/src/carry/`, `operator/scripts/` and `docs/`. Nothing imports from ~/scope. One fix: `receipt.ts` called `require()`, which breaks under ESM, and now uses an import.
- **D-P0-3 (2026-11-07) Dependencies.** Operator dependencies are pinned to the exact versions in scope's lockfile. Web reuses scope's package-lock (Next 15.5, React 19.1, wallet-selector 10.1.4).
- **D-P0-4 (2026-11-07) Branch.** Work happens on `master`, which is the local default, and is pushed to `origin/master`.
- **D-P0-5 (2026-11-07) Safety default.** The operator runs with `DRY_RUN=1` unless it is explicitly set to `0`. Nothing is signed or submitted against mainnet without Amit's OK.
- **D-P1a (2026-11-07) The vault key is MPC-controlled. The operator holds no vault key.**
  - **Question.** Can a contract-controlled ed25519 key (Chain Signatures, EdDSA domain) be registered on intents.far and sign transfer intents?
  - **Answer: yes.** It needs no registration.
  - **Source.** From near/intents at `32cd1f97` (2026-11-04):
    - `intents.far` is the defuse contract built with `--features far`, which is `imt` plus a DAO-only `force_add_public_keys`, deployed on the separate FAR chain. A NEAR contract therefore cannot authenticate there as the predecessor. Accounts on FAR sign `MultiPayload`s instead.
    - An implicit account (`hex(ed25519 pk)`) is authorised by its own key without `add_public_key` (`PublicKey::from_implicit_account_id`). NEP-413 verification is `ed25519.verify(pk, sha256(borsh((2^31+413, payload))), sig)` (`crates/signatures/nep413`).
    - The intents team ships an on-chain MPC ed25519 signer for exactly this purpose (`crates/mpc/signer`: `Payload::Eddsa`, `MAINNET_MPC_CONTRACT_ID = v1.signer`).
  - **Test.** `operator/scripts/p1-mpc-eddsa-probe.ts`, record in `docs/probes/p1-mpc-eddsa.json`:
    - Testnet MPC `v1.signer-prod.testnet` has domain 1 = FROST (EdDSA), Running.
    - The key derived for `(sp-probe-1794059432.testnet, "silent-partner/vault/probe")` is implicit account `da0d924d…0c77`. MPC `sign` with `payload_v2.Eddsa = NEP-413 prehash` returned an Ed25519 signature in 6.5 s, and it verifies locally.
    - A mainnet **read-only** `simulate_intents` on `intents.near` accepted the signed payload (`intents_executed` for that implicit account). The tampered copy panicked with `invalid signature`.
  - **Not tested directly.** The FAR-chain endpoint itself (intents.far). It runs the same verifier crate, and the recipient string is the only difference (`intents.far`). The first real check is the $1 round trip in NEEDS-AMIT.md.
  - **Design consequence.**
    - The vault's confidential account is the implicit account of `derived_public_key(vault_contract, "silent-partner/vault/<id>", domain 1)`.
    - The contract builds each intent message itself and asks `v1.signer` to sign it. It signs only:
      - (i) a transfer to a 1Click deposit address taken from a 1Click-signed, non-dry quote that the contract verifies on-chain (signature code carried over from scope; amount bound to `amountIn`);
      - (ii) withdrawals to the withdrawing holder's registered exit account;
      - (iii) in emergency mode, pro-rata exits that anyone can trigger.
    - The operator chooses trades and posts NAV but cannot move funds anywhere else. That is the trust assumption the README will state.
  - **Fallback.** If 1Click limit orders (no signed quote) are needed, the contract allows a transfer to an order deposit address only when the operator co-signs and the amount is ≤ the signal's % of NAV. Recorded as an operator-trust exception in the threat model.
- **D-P1b (2026-11-07) Round-trip path.**
  - **Route.** Public `intents.near` USDC → 1Click shield (`INTENTS → CONFIDENTIAL_INTENTS`, same asset) → unshield (`CONFIDENTIAL_INTENTS → INTENTS`). This needs no origin chain and has 0 app fees (dry quotes, `docs/probes/p1-roundtrip-dry.json`).
  - **Script.** `operator/scripts/roundtrip.ts` is dry by default. Live mode needs `ROUNDTRIP_LIVE=1` plus the account id typed at the prompt, and Amit runs it himself.
  - **Vault deposits.** The same shield route will carry follower deposits into the vault: a follower deposits to the vault's public intents account, and the operator shields.
- **D-P1c (2026-11-07) No OutLayer.** The operator is our own service.
  - **Cost.** OutLayer costs 0.0015 NEAR per 5 s run on-chain (live `get_pricing`), or needs a $1 prepaid key for HTTPS.
  - **Why not.** It would only attest the NAV computation, and P1a already removes the operator's custody. That's not worth a payment dependency before the deadline. It can be added later only if Amit approves the payment.
- **D-P2-1 (2026-11-07) What the vault key may sign.** `sign_intent` accepts four shapes and nothing else. The message JSON is parsed strictly: unknown fields are rejected, so there's no `memo` and no `msg` notification, and the transfer is exactly one intent of one token.
  - **Login:** empty intents for intents.near. Operator only.
  - **Shield:** INTENTS→CONFIDENTIAL_INTENTS, same asset, paying and refunding the vault.
  - **Trade:** confidential→confidential between `allowed_assets`, paying and refunding the vault, slippage ≤ `max_slippage_bps`.
  - **Payout:** base asset CONFIDENTIAL_INTENTS→INTENTS to the claim's `exit_account`, amount ≤ what the claim still has open.
  - **Binding for transfers:** each transfer needs a 1Click-signed non-dry quote under the immutable `oneclick_key`. The receiver must equal the quote's `depositAddress` and the amount its `amountIn`. The token is `imt:<treasury>:<originAsset>` (FAR) or `originAsset` (intents.near), set by `depositType`. The deadline must be ≤ the quote's and ≤ now+1h.
- **D-P2-2 (2026-11-07) Limit orders run in the operator.** 1Click limit orders have no signed quote, so the contract cannot bind their deposit address. A "limit" signal is therefore held by the operator, and executed as a signed confidential quote when the price crosses. Every fill still goes through D-P2-1.
- **D-P2-3 (2026-11-07) Payout settlement.** A signed payout is held "in flight" until its intent deadline.
  - **Normal mode.** The operator marks it executed at any time, or releases it, but only after the deadline, when it can no longer execute.
  - **Emergency mode.** In-flight payouts stay counted as paid. That's the safe side for the holders who remain, and the residual risk is written up in the threat model.
- **D-P2-4 (2026-11-07) Deposits.** Deposits arrive by NEP-141 `ft_transfer_call` of the base asset to the contract, with an empty msg. Shares are minted at the book NAV: the last NAV, plus deposits since, minus payouts since. When `intents_contract` is set (mainnet), funds are forwarded to `intents.near` with msg = the vault's implicit account, and the operator shields them.
  - **Refunded, not minted:** before activation, when NAV is stale or in emergency, below `min_deposit`, and when a follower deposit would push the leader under `min_leader_bps`.
  - **Seeding.** The leader seeds the vault first.
- **D-P2-5 (2026-11-07) Testnet quote key.** 1Click has no testnet, so the testnet vault's `oneclick_key` is a test key and the operator signs quotes the way 1Click does (`operator/src/testquote.ts`). On mainnet the key is fixed at init to `ed25519:reYaWhvwu8Jzo3WUM3zhn6VrhuMEF4eADL17qtRVifc`, and anyone can check it with `get_config`.
- **D-P2-6 (2026-11-07) Gas.** `sign_intent` forwards 100 TGas to MPC `sign` and 15 TGas to the callback, and is called with 300 TGas. That worked on testnet: `docs/testnet.md`.
- **D-P3-1 (2026-11-07) The contract mints, not the operator.** Shares are minted in `ft_on_transfer` at deposit time. The operator doesn't call "mint", so a down or malicious operator can't withhold or misprice a deposit beyond the last posted NAV. The operator's deposit job is to shield the vault's public balance into the confidential account.
- **D-P3-2 (2026-11-07) Fees come from contract accounting, not 1Click appFees.** The leader's performance fee is minted as shares above the HWM, on-chain. Adding appFees would charge on trade volume rather than on gains, and it would also leak trading activity to the fee recipient's balance. Our only appFee is the 20 bps 1Click partner tier.
- **D-P3-3 (2026-11-07) NAV.** NAV = (public base balance not yet shielded) + Σ confidential holdings, each valued by a 1Click dry quote into the base asset (what the vault could actually realise), − what open claims are still owed. Claimed shares are already burned, so leaving the owed amount in would inflate the price for everyone else. The breakdown (positions) never leaves the operator. Only NAV and the fill-log head are published.
- **D-P3-4 (2026-11-07) Dry mode is paper trading.** With `DRY_RUN=1` (the default), fills, shields and payouts are written to the log marked `dry`, priced by real dry quotes. The ledger and NAV then behave exactly as in live mode, and the vault key is never used. Chain writes (NAV, signals) are on by default on testnet. On mainnet they need `MAINNET_WRITES=1`, and live mainnet needs `MAINNET_LIVE_OK=1`. Both are Amit's call.
- **D-P3-5 (2026-11-07) Expired payouts.** The operator releases an expired in-flight payout only if it submitted the payout itself and 1Click reports it as terminal and not SUCCESS. It does not release unknown ones: `on_signed` logs the signature publicly, and someone could have submitted it. (It would still pay the right person, but releasing it as well would pay twice.)
