# Decisions

Each decision is dated, with its reason.

- **D-P0-1 (2026-11-07) Toolchain.** Rust 1.98.1 with near-sdk 5.30 and cargo-near 0.22.0, the same pin as ~/scope. That keeps the reproducible-build image identical.
- **D-P0-2 (2026-11-07) Carry-over.** Files are copied into `operator/src/carry/`, `operator/scripts/` and `docs/`. Nothing imports from ~/scope. One fix: `receipt.ts` called `require()`, which breaks under ESM, and now uses an import.
- **D-P0-3 (2026-11-07) Dependencies.** Operator dependencies are pinned to the exact versions in scope's lockfile. Web reuses scope's package-lock (Next 15.5, React 19.1, wallet-selector 10.1.4).
- **D-P0-4 (2026-11-07) Branch.** Work happens on `master`, which is the local default, and is pushed to `origin/master`.
- **D-P0-5 (2026-11-07) Safety default.** The operator runs with `DRY_RUN=1` unless it is explicitly set to `0`. Nothing is signed or submitted against mainnet without Amit's OK.
- **D-P1a (2026-11-07) The vault key is MPC-controlled. The operator holds no vault key.**
  - **Question.** Can a contract-controlled ed25519 key (Chain Signatures, EdDSA domain) be registered on intents.far and sign transfer intents?
  - **Answer: yes.** It needs no registration.
  - **Source.** From near/intents at `32cd1f97` (2026-11-04):
    - `intents.far` is the defuse contract built with `--features far`, which is `imt` plus a DAO-only `force_add_public_keys`, deployed on the separate FAR chain. A NEAR contract therefore cannot authenticate there as the predecessor. Accounts on FAR sign `MultiPayload`s instead.
    - An implicit account (`hex(ed25519 pk)`) is authorised by its own key without `add_public_key` (`PublicKey::from_implicit_account_id`). NEP-413 verification is `ed25519.verify(pk, sha256(borsh((2^31+413, payload))), sig)` (`crates/signatures/nep413`).
    - The intents team ships an on-chain MPC ed25519 signer for exactly this purpose (`crates/mpc/signer`: `Payload::Eddsa`, `MAINNET_MPC_CONTRACT_ID = v1.signer`).
  - **Test.** `operator/scripts/p1-mpc-eddsa-probe.ts`, record in `docs/probes/p1-mpc-eddsa.json`:
    - Testnet MPC `v1.signer-prod.testnet` has domain 1 = FROST (EdDSA), Running.
    - The key derived for `(sp-probe-1794059432.testnet, "silent-partner/vault/probe")` is implicit account `da0d924d…0c77`. MPC `sign` with `payload_v2.Eddsa = NEP-413 prehash` returned an Ed25519 signature in 6.5 s, and it verifies locally.
    - A mainnet **read-only** `simulate_intents` on `intents.near` accepted the signed payload (`intents_executed` for that implicit account). The tampered copy panicked with `invalid signature`.
  - **Not tested directly.** The FAR-chain endpoint itself (intents.far). It runs the same verifier crate, and the recipient string is the only difference (`intents.far`). The first real check is the $1 round trip in NEEDS-AMIT.md.
  - **Design consequence.**
    - The vault's confidential account is the implicit account of `derived_public_key(vault_contract, "silent-partner/vault/<id>", domain 1)`.
    - The contract builds each intent message itself and asks `v1.signer` to sign it. It signs only:
      - (i) a transfer to a 1Click deposit address taken from a 1Click-signed, non-dry quote that the contract verifies on-chain (signature code carried over from scope; amount bound to `amountIn`);
      - (ii) withdrawals to the withdrawing holder's registered exit account;
      - (iii) in emergency mode, pro-rata exits that anyone can trigger.
    - The operator chooses trades and posts NAV but cannot move funds anywhere else. That is the trust assumption the README will state.
  - **Fallback.** If 1Click limit orders (no signed quote) are needed, the contract allows a transfer to an order deposit address only when the operator co-signs and the amount is ≤ the signal's % of NAV. Recorded as an operator-trust exception in the threat model.
- **D-P1b (2026-11-07) Round-trip path.**
  - **Route.** Public `intents.near` USDC → 1Click shield (`INTENTS → CONFIDENTIAL_INTENTS`, same asset) → unshield (`CONFIDENTIAL_INTENTS → INTENTS`). This needs no origin chain and has 0 app fees (dry quotes, `docs/probes/p1-roundtrip-dry.json`).
  - **Script.** `operator/scripts/roundtrip.ts` is dry by default. Live mode needs `ROUNDTRIP_LIVE=1` plus the account id typed at the prompt, and Amit runs it himself.
  - **Vault deposits.** The same shield route will carry follower deposits into the vault: a follower deposits to the vault's public intents account, and the operator shields.
- **D-P1c (2026-11-07) No OutLayer.** The operator is our own service.
  - **Cost.** OutLayer costs 0.0015 NEAR per 5 s run on-chain (live `get_pricing`), or needs a $1 prepaid key for HTTPS.
  - **Why not.** It would only attest the NAV computation, and P1a already removes the operator's custody. That's not worth a payment dependency before the deadline. It can be added later only if Amit approves the payment.
- **D-P2-1 (2026-11-07) What the vault key may sign.** `sign_intent` accepts four shapes and nothing else. The message JSON is parsed strictly: unknown fields are rejected, so there's no `memo` and no `msg` notification, and the transfer is exactly one intent of one token.
  - **Login:** empty intents for intents.near. Operator only.
  - **Shield:** INTENTS→CONFIDENTIAL_INTENTS, same asset, paying and refunding the vault.
  - **Trade:** confidential→confidential between `allowed_assets`, paying and refunding the vault, slippage ≤ `max_slippage_bps`.
  - **Payout:** base asset CONFIDENTIAL_INTENTS→INTENTS to the claim's `exit_account`, amount ≤ what the claim still has open.
  - **Binding for transfers:** each transfer needs a 1Click-signed non-dry quote under the immutable `oneclick_key`. The receiver must equal the quote's `depositAddress` and the amount its `amountIn`. The token is `imt:<treasury>:<originAsset>` (FAR) or `originAsset` (intents.near), set by `depositType`. The deadline must be ≤ the quote's and ≤ now+1h.
- **D-P2-2 (2026-11-07) Limit orders run in the operator.** 1Click limit orders have no signed quote, so the contract cannot bind their deposit address. A "limit" signal is therefore held by the operator, and executed as a signed confidential quote when the price crosses. Every fill still goes through D-P2-1.
- **D-P2-3 (2026-11-07) Payout settlement.** A signed payout is held "in flight" until its intent deadline.
  - **Normal mode.** The operator marks it executed at any time, or releases it, but only after the deadline, when it can no longer execute.
  - **Emergency mode.** In-flight payouts stay counted as paid. That's the safe side for the holders who remain, and the residual risk is written up in the threat model.
- **D-P2-4 (2026-11-07) Deposits.** Deposits arrive by NEP-141 `ft_transfer_call` of the base asset to the contract, with an empty msg. Shares are minted at the book NAV: the last NAV, plus deposits since, minus payouts since. When `intents_contract` is set (mainnet), funds are forwarded to `intents.near` with msg = the vault's implicit account, and the operator shields them.
  - **Refunded, not minted:** before activation, when NAV is stale or in emergency, below `min_deposit`, and when a follower deposit would push the leader under `min_leader_bps`.
  - **Seeding.** The leader seeds the vault first.
- **D-P2-5 (2026-11-07) Testnet quote key.** 1Click has no testnet, so the testnet vault's `oneclick_key` is a test key and the operator signs quotes the way 1Click does (`operator/src/testquote.ts`). On mainnet the key is fixed at init to `ed25519:reYaWhvwu8Jzo3WUM3zhn6VrhuMEF4eADL17qtRVifc`, and anyone can check it with `get_config`.
- **D-P2-6 (2026-11-07) Gas.** `sign_intent` forwards 100 TGas to MPC `sign` and 15 TGas to the callback, and is called with 300 TGas. That worked on testnet: `docs/testnet.md`.
- **D-P3-1 (2026-11-07) The contract mints, not the operator.** Shares are minted in `ft_on_transfer` at deposit time. The operator doesn't call "mint", so a down or malicious operator can't withhold or misprice a deposit beyond the last posted NAV. The operator's deposit job is to shield the vault's public balance into the confidential account.
- **D-P3-2 (2026-11-07) Fees come from contract accounting, not 1Click appFees.** The leader's performance fee is minted as shares above the HWM, on-chain. Adding appFees would charge on trade volume rather than on gains, and it would also leak trading activity to the fee recipient's balance. Our only appFee is the 20 bps 1Click partner tier.
- **D-P3-3 (2026-11-07) NAV.** NAV = (public base balance not yet shielded) + Σ confidential holdings, each valued by a 1Click dry quote into the base asset (what the vault could actually realise), − what open claims are still owed. Claimed shares are already burned, so leaving the owed amount in would inflate the price for everyone else. The breakdown (positions) never leaves the operator. Only NAV and the fill-log head are published.
- **D-P3-4 (2026-11-07) Dry mode is paper trading.** With `DRY_RUN=1` (the default), fills, shields and payouts are written to the log marked `dry`, priced by real dry quotes. The ledger and NAV then behave exactly as in live mode, and the vault key is never used. Chain writes (NAV, signals) are on by default on testnet. On mainnet they need `MAINNET_WRITES=1`, and live mainnet needs `MAINNET_LIVE_OK=1`. Both are Amit's call.
- **D-P3-5 (2026-11-07) Expired payouts.** The operator releases an expired in-flight payout only if it submitted the payout itself and 1Click reports it as terminal and not SUCCESS. It does not release unknown ones: `on_signed` logs the signature publicly, and someone could have submitted it. (It would still pay the right person, but releasing it as well would pay twice.)
- **D-P4-1 (2026-11-07) Signal key.** Wallets (MyNearWallet, Meteor) can sign NEP-413 envelopes but not raw bytes. The leader therefore registers a browser-held ed25519 key on the vault with one wallet transaction (`set_signal_key`), and the console signs signals locally with it. The key is authorised by the leader's NEAR account on-chain. Rotating it takes another wallet transaction, and losing it only stops signalling, because it moves no funds.
- **D-P4-2 (2026-11-07) Static export.** Pages take `?id=<vault>`, because a static export has no dynamic routes. Every number on the site is read from NEAR RPC in the browser. The browser also re-verifies every NAV attestation against the vault's `attestation_key`, and the share card states how many verified.
- **D-P4-3 (2026-11-07) What the site shows.** Return since inception, from the post-fee share price; max drawdown; AUM as a bucket; NAV epochs; signal hashes. No positions and no exact AUM. The exact `book_nav` is public on-chain anyway; the bucket just avoids putting it on a leaderboard.
- **D-P4-4 (2026-11-07) Playwright stays out of CI.** The specs read live testnet and the leader test needs the local operator and keys, so they run locally (`make e2e`, `make screens`). CI runs the deterministic unit tests: metrics, attestation verification, and the signal vector shared with the operator.
- **D-P5-1 (2026-11-07) Code lock.** The vault account's full-access key can redeploy the contract. For the small-funds mainnet demo we keep it, so a bug can be fixed, and the README and threat model say so. For production: delete the full-access key after deploy (`near account delete-keys`) and verify the reproducible-build hash, so nobody (us included) can change what the MPC key will sign.
- **D-P5-2 (2026-11-07) Mainnet parameters.**
  - **Assets.** Base asset: native USDC (`17208628…33a1`). Allowed assets: USDC and wNEAR.
  - **Fees and limits.** 20% performance fee, 10% minimum leader stake, 1% max slippage, 1 USDC minimum deposit.
  - **Keys.** The attestation key was generated locally (`operator/data/mainnet-keys.json`, gitignored); its public key is in `docs/mainnet-init.json`.
- **D-P1a, follow-up (2026-11-07) Execution confirmed, not just simulation.**
  - **Test.** The real defuse verifier (near/intents `releases/defuse-0.2.10.wasm`) was deployed on testnet, with a vault pointed at it. That defuse contract's `execute_intents` executed a transfer signed by the vault's MPC key through `sign_intent`. Deposit forwarding into the vault's MPC account also worked (docs/testnet.md).
  - **Contract change.** The NEP-413 recipient of intents.near-side payloads (shield, login) is now the configured `intents_contract`, which defaults to `intents.near`. It had been hardcoded. The FAR side stays `intents.far`.
- **D-P5-3 (2026-11-07) Mainnet artifact.** `cargo near build reproducible-wasm` at commit `5afff30` produced sha256 `f8b07eb152a69e8551ec058383efd82ae89c65abcf246a61baf82cce21f5a2bc` (code hash base58 `HjnCic8REmu5hCixfquUHCPVzRRBWYnbZkHaHKgh8cLB`, 310,022 bytes). If the contract changes before the deploy, rebuild and update the runbook.
- **D-S-1 (2026-11-09) Contract changes before the season deploy.** The season vaults are new deployments, so everything later items need from the contract went in first, to avoid a state migration:
  - `get_position(account)`: per-holder `deposited` and `claimed`, for P&L (item 6).
  - `SignKind::PublicPayout{claim_id}`: a direct base-asset transfer from the vault's *public* intents balance to a claim's exit account, no quote. Operator any time; anyone for emergency claims. This closes the "public leg" gap in the threat model: unshielded funds can leave without 1Click (item 3).
  - In emergency the claimant may confirm (`settle_payout(executed = true)`) their own payout, since the operator may be gone. Only the operator can release.
  - Cargo feature `drill`: NAV goes stale after 5 minutes instead of 24h, and `new` refuses any account outside `.testnet`. The release (mainnet) build doesn't contain it.
  - The mainnet wasm hash in NEEDS-AMIT §3 is stale until rebuilt. It will be rebuilt after item 7's hardening, and §3 updated.
- **D-S-2 (2026-11-09) Paper pricing in CI uses public 1Click dry quotes.** Confidential quotes need the partner JWT ("User authentication is required for confidential intent quotes"). That JWT is a mainnet credential, so it stays out of GitHub. In CI, paper fills and NAV valuation use dry quotes on the public `INTENTS` legs: same solvers and assets, real 1Click-signed quotes, verified like any other, and no key needed. Run locally with the JWT, the operator still prices on confidential legs.
- **D-S-3 (2026-11-09) Season state is sealed in git.** Fill logs (positions) and bot notebooks (decisions, AI rationales) live encrypted (AES-256-GCM, key in a repo secret) on the orphan `season-state` branch, committed after every tick. CI logs and `last-run.json` are public, so the runner prints only what the chain already shows (epoch, NAV, tx, signal hash). Bot targets and trade sizes would reveal positions, so they're never printed.
- **D-S-4 (2026-11-09) Season keys are testnet-only and separate.** The season has its own operator account (`sp-sop-92991.testnet`) and attestation key, so the keys in GitHub secrets control nothing else. Secrets: operator key, attestation key, the three bot signal keys, and the state key. The manual leader's signal key stays local. No mainnet key or credential is in GitHub.
- **D-S-5 (2026-11-09) Manual leader signals go through `workflow_dispatch`.** `scripts/season-signal.ts` signs locally, and `gh workflow run season.yml -f signal=…` hands the envelope to the next tick. The input is visible in the run at the moment the signal executes, which is the same moment its hash goes on-chain.
- **D-S-6 (2026-11-09) Honest labels.** Every vault carries a mode chip ("paper · testnet", or "live · mainnet" once there is one), and the leaderboard explains what paper means. The operating status "live" was renamed "active", so it can't be read as "real money".
- **D-S-7 (2026-11-09) Accounts.** The faucet rate-limited after 10 new accounts, so existing testnet accounts serve as the followers (`sp-follower-60270`, `sp-fund-61557`) and as the drill leader (`sp-leader-60270`).
- **D-AI-1 (2026-11-09) AI leader.** `operator/src/leaders/ai.ts`.
  - **Input.** Each epoch, one chat completion on NEAR AI Cloud (`https://cloud-api.near.ai/v1`, OpenAI-compatible) with only public data: a summary of CoinGecko's 24h NEAR/USD 5-minute series (price, returns, EMAs, volatility, range), plus the vault's current NEAR exposure.
  - **Output.** `{target_exposure, rationale}`. The target is clamped to [0, 0.9] and rounded to 0.05, and a null or unparseable reply holds. `rebalance` turns it into one signed signal, the same way as for the bots.
  - **Privacy.** The rationale (with the NEAR AI chat id, for its TEE signature) goes only into the sealed notebook. The signal carries `memo_hash = sha256(rationale)`, so the signal hash on-chain commits to it. `scripts/season-disclose.ts` reveals one signal plus its rationale and checks both against the chain.
  - **Model.** The default is `deepseek-ai/DeepSeek-V4.1-Flash-1017`, which is served from NEAR AI's attested TEE infrastructure, so even the inference host doesn't see the rationale in the clear. It's cheap (about $0.05/day at 96 epochs).
  - **Without `NEARAI_API_KEY`,** the AI vault holds and still posts NAV (NEEDS-AMIT §7).
  - **Tracks.** The AI is a leader, not the operator, so by the original rule the hackathon tracks stay privacy + defi. Mentioning the AI leader in the agents track is Amit's call.
- **D-E-1 (2026-11-09) Emergency drill and UI.**
  - **The drill.** It runs against a vault built with `--features drill`, because a 24h wait doesn't fit a demo. Every other code path is the release code.
  - **Payout path.** The follower is paid by `PublicPayout` from the public balance. In paper mode nothing was ever shielded, so that's where the funds are. On mainnet, shielded funds would first need a 1Click unshield (Trade/Payout quotes, which anyone may submit in emergency).
  - **Vault page.** It shows the state: a stale-NAV notice with "Trigger emergency", then the emergency banner with "Exit at last NAV" and the exit value (shares × book NAV / total). Each emergency claim gets four wallet steps: the vault signs, execute on the verifier, withdraw to wallet, mark paid. The signature is read from the `on_signed` log of the sign transaction, and the payload is kept in localStorage across wallet redirects.
  - **View as.** `?as=<account>` shows any account's position read-only. Share balances and claims are public on-chain anyway, and every action still needs the wallet. It makes the screens and the drill reviewable without a wallet.
- **D-W-1 (2026-11-09) "What the chain sees" (`/chain/`).** One vault, three columns.
  - **Observer and follower** are live RPC reads. The follower column uses `get_position` for P&L, and it says plainly that share balances are public too.
  - **Leader and operator** are private by design. For the demo we publish one vault's fill log and its signals up to the latest complete NAV epoch (`scripts/season-snapshot.ts` → `web/public/disclosures/<vault>.json`). The browser then checks four things: the hash chain from genesis; that every on-chain NAV head is the log's NAV entry with the same value; that every recorded signal's fill hash is in the log; and that the disclosed signal hashes to the on-chain hash.
  - **Vault choice.** The disclosed vault is the manual-leader paper vault. Publishing a log reveals that vault's past positions, which is acceptable for a testnet paper vault and is exactly what a leader would do to prove a track record. Manual signals are kept in the leader's local record (`data/season-manual-signals.jsonl`), and the bots' signals in their sealed notebooks.
- **D-W-2 (2026-11-09) Landing page and GitHub Pages.** `/` is now the landing page: hero, three steps, for leaders and for followers, and links to the leaderboard, `/chain/` and the docs. Live stats are read from the chain on load. The leaderboard moved to `/leaderboard/`, with sortable columns and sparklines. `.github/workflows/pages.yml` builds the static export with `basePath=/silent-partner` and deploys on every push that touches `web/`. The build has no secrets, and every number is read in the visitor's browser. URL: https://amityadav0.github.io/silent-partner/. The leader console still posts to an operator API (`NEXT_PUBLIC_OPERATOR_API`, default localhost). On Pages that's only reachable when you run the operator locally, and paper-season manual signals go through `workflow_dispatch` (D-S-5).
- **D-U-1 (2026-11-09) UX pass.**
  - **Position.** P&L comes from the contract's per-holder cost basis: value at book price + withdrawn − deposited. Vaults deployed before D-S-1 say they predate it.
  - **Withdrawals.** Each one is a track: requested (cancellable, burns at the next NAV) → burned at NAV (claim) → paying (payout signed or in flight) → paid. Emergency claims carry their self-service payout steps.
  - **Create-vault wizard (`/create/`).** It produces the exact `new(cfg)` args, checked with the contract's own limits, plus near-cli-rs commands to deploy, init and activate. It never deploys anything itself. Mainnet has no Silent Partner operator yet, so the wizard requires your own operator there.
  - **Leaderboard.** Sort by return, drawdown, AUM, epochs or name. Each row has a sparkline of the last 96 epochs.
  - **RPC fallback.** Browser RPC reads fall through fastnear → drpc → near.org on a 429 or network error, with backoff between rounds. The public testnet RPC rate-limits bursts, and a 429 surfaces as "Failed to fetch".
  - **Screens.** docs/screens/ was refreshed with landing, leaderboard (desktop and mobile), vault-as-follower, chain, emergency, emergency claim paid, create, leader, share and vault-mobile.
- **D-H-1 (2026-11-09) Property tests and the leader-stake fix.**
  - **Share math** (`math.rs`, proptest, 2000 cases each): a mint never gives more value than was paid, and the holders' price never falls. A burn never pays more than pro rata. The fee is charged only above the HWM, never takes holders below it, and the fee shares are worth at most the fee.
  - **Contract** (`prop_tests.rs`): random sequences of up to 60 operations (deposits, withdrawal requests and cancels, NAV posts from −60% to +60%, emergency, exits) run against the real `Vault`. After every step they check share conservation, `book_nav = deposits + operator gains − claims` exactly, dust ≤ 1 unit per holder (and it stays in the vault), the cost-basis totals, a non-decreasing HWM, and the leader's minimum stake outside emergency. CI runs 400 cases; a 3000-case sweep passed locally.
  - **The bug it found.** The leader-stake check for deposits counted the leader's *locked* shares, which burn at the next NAV. So a leader could lock shares, a follower could then deposit, and the leader would fall under the minimum at the next post. The leader's own request check also counted other holders' pending withdrawals as gone, though they can cancel. Both checks are now conservative: only the leader's free shares count, and only the leader's own pending shares count as leaving. Regression test: `leader_locked_shares_do_not_count_toward_the_stake`. The season vaults run the earlier code, which is fine for paper vaults. The mainnet artifact will be rebuilt from this code.
